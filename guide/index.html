What this is

Lessons from projects written mostly by an agent

Claude Code wrote most of the code in the {{projects}} projects below, with one person deciding what to build. Their histories were read commit by commit, and every failure that repeated, and every fix that held, was written down as a finding. The rules on this site are built from those findings, and each rule says which findings it rests on.

The one idea

The agent is fast. It also grades its own work.

An agent will tell you a task is done, a test passes or a rule was followed, and it believes it. Across these projects, those claims were often wrong in ways nobody saw until later. So the practice moves trust away from what the agent says and onto things that can be checked: files, tools, tests and the person.

  1. You decidewhat to build next, and what counts as done
  2. The plan is a filea backlog written through a tool, never by hand
  3. Claude Code workson one task, under guards that refuse unsafe edits
  4. Checks decidetests, lint and CI pass before anything is called done
  5. One commitholding one task and nothing else, then back to you

What to keep in mind

Eight things the projects learned the hard way

Each card is one lesson in plain words. The tags under it are the proof: an F tag opens a finding with its sources, and a rule tag opens the rule that turns it into something you can adopt.

📜

1. Keep the always-read file short

Claude Code reads CLAUDE.md, and everything it imports, at the start of every conversation, so every line in it is paid for on every turn. In the projects studied it kept growing until an automatic check refused the next addition. A note saying "keep this short" did not stop it.

What worked: make it an index, move what only some tasks need into skills that load when needed, and give those files a size limit of their own.

Evidence F1F2F3 Rules IS-1IS-2IS-4
🛡

2. If a rule matters, make a machine check it

Rules that lived only as sentences were broken, including by the repository that wrote them. An instruction to keep planning notes brief was ignored; a limit that refused the text at the moment it was written held.

What worked: for every rule the agent actually broke, add a hook or a test that fails when it breaks again, and let the sentence point to it.

Evidence F300F5F101 Rules GH-1AW-2
📋

3. Keep the plan in files a tool writes

The backlog, the changelog and the decisions live in the repository, where the next session can read them, and a tool writes them so their shape cannot drift. Agents also file tasks that describe nothing wrong, and designs written up front were often overturned once the work began.

What worked: record the problem rather than the planned fix, and file a task only when something is actually wrong or missing.

Evidence F100F102F103 Rules PG-1PG-2CD-5
📦

4. One task, one commit, staged by name

A written "one task per commit" rule did not prevent commits that shipped several tasks. Commit tools that stage everything swept in logs and other sessions' work, and two sessions sharing a folder committed each other's changes.

What worked: close each task before starting the next, and add files by path, never git add -A.

Evidence F203F200F201 Rules CD-1CD-3CS-2
✅

5. "Done" means a check passed, on every push

Checks that ran only on one machine let failing tests reach the main branch without anyone noticing. Tasks were closed with no check covering what was committed, and some checks reported a pass over work that never ran.

What worked: run the checks in CI on every push, treat "could not run" as a failure, and never call a task done before its checks pass.

Evidence F303F305F302 Rules VG-1VG-3VG-5
🔢

6. Never type a number into the docs

A count or a list written by hand goes stale without a sound when the thing it describes changes. This happened in all five projects.

What worked: generate figures from the source, or check them against it. Every number on this page is computed when the site is built.

Evidence F7 Rules AW-1IS-5
🧑

7. Some things only a person can close

Work that needs a person's judgement, or hardware the machine does not have, cannot be finished by the agent. Tasks recorded as shipped were later found not to work, because the record held the agent's own claim.

What worked: let that work wait with its reason written down, and let the person set the bar for "good enough".

Evidence F105F104 Rules HR-1HR-2PG-6
🔌

8. Watch the seams between tools

Text passing through a Windows shell, a codec or a line-ending conversion changed silently, in all five projects. Where several copies of a tool were installed, sessions ran an old or unintended one without noticing.

What worked: declare line endings and encodings, check them byte by byte, and make sure exactly one copy of each tool answers.

Evidence F404F403 Rules EP-2EP-5EP-1

Get started

Starting a new project, in eight steps

The order matters: each step protects the next. The guards exist before the first plan file, and the checks exist before the first feature. The repository ships templates for every file, so you fill them in rather than write them.

1

Copy the templates

One script writes the instruction file, settings, skills, ignore rules, line-ending rules and a CI workflow.

2

Turn on the guards

Hooks refuse hand edits of the planning files and ask before a push or a hard reset.

3

Create the plan

The planning tool writes the backlog, changelog and decisions, with length limits on what goes in them.

4

Write the short file

Describe the project in a short index, then set its size budget just above where it landed.

5

Write the house rules

A commit skill (one task per commit, stage by path) and a writing skill (language, style).

6

Pick a level

Choose how far to go, 1, 2 or 3, and record it where the checker reads it.

7

Put the checks in CI

Your build and tests run on every push, before the first feature is written.

8

Check, then commit

Run the conformance checker, fix what it reports, and make a first commit with no code in it.

Six choices are yours, not the agent's, such as whether commits name the agent and how broad its permissions are. The full walkthrough, with the commands, is the new-project guide. For an existing codebase, or one that has drifted, see the existing-project and realignment guides.

How far to go

Three levels, each a sensible place to stop

You do not have to adopt everything at once. Each level includes the one before it.

Level 1

Governed

The agent is told little and precisely, planning goes through tool-written files, and each task lands as its own commit. Costs a config file, a planning tool and a habit.

Level 2

Gated

Nothing is done until a check passes, checks run in CI on every push, and guards stand behind the rules the agent broke. Most recorded failures were stopped here.

Level 3

Measured

What the project says about itself is generated or checked: figures, lists and size limits. Costs the most, and pays off as the project grows.

How sure is this?

Every finding says how solid it is

Each finding gets two grades. Recurrence says how widely it was seen, from R1 (once, in one project) to R4 (in all five). Strength says how well it was established, from S1 (someone wrote it down) through S2 (an incident was recorded) and S3 (it was counted) to S4 (a test fails when it stops holding).
